## Principles I will work by

1. **Measure, change, measure.** Each PR that touches engine, DSP or protocol states its before and after
   from the same harness, and the facts land in `facts/`.
2. **One engine, one description of each thing.** One module descriptor (the C++), one protocol schema, one
   patch codec per language generated from one schema. Generated files are checked for drift, never
   hand-kept in sync.
3. **The core knows categories, not modules.** No module ID appears in engine, sidecar or Studio core.
   A module declares what it needs (MIDI in, a message bus, telemetry, tables); the host provides it.
4. **Deterministic tools.** New, check, test, build, convert are scripts with plain error messages.
5. **Small vertical steps on `main`.** Every merge leaves main green and the bundled patches rendering the
   same, so any block can end cleanly.

## Phases

The order is by dependency: nothing can be judged before Phase 0; live editing and the module format both
want the single engine; sound fixes want the live-edit and golden harness; categories and UIs want the
module format.

### Phase 0 — A measurement floor (bench and tests only)
Close the holes in audit §8 so every later change can be judged.
1. Fix the harness: 12 soak failures, chord probe, `Six_Essentials_Demo.json`, denormal injection,
   Windows DSP/perf, the Windows CTest and desktop failures.
2. **Golden renders**: all 24 bundled patches (+ yours), per architecture, as the D4 gate.
3. **Edit-continuity test**: render while applying each kind of edit; record phase reset, silence length
   and largest sample jump. This is the yardstick for Phase 2.
4. Replace the click metric; add a baseline to the zipper metric; add 44.1/96 kHz runs and CHAOS aliasing.
5. A benchmark gate in CI: instruction count per block on fixed graphs (stable on shared runners).
6. Fold in the Pi 60-minute, Windows 15-minute and cross-tool results when they land; revise targets.

*Exit:* a baseline table `facts/BASELINE.md` with every target row filled or marked device-only.

### Phase 1 — One engine
1. Freeze ABI1 reference renders as data; delete `native/src`, `native/modules`, `native/tests`, the
   provider bridge and the shim branches (D1).
2. Replace the ABI1 types in the facade, patch loader, sidecar, web build and tools with engine-native
   ones; remove `legacy_index` from loader paths (D2, D3).
3. Rename and lay out the tree (below); retire Qt wording, dead options and issue-number comments.
4. Format the core; split `process_node`, `Session::apply` and the config adapter into reviewable units,
   with no behaviour change.
5. Connect transport (tempo, play/stop) through the facade.

*Gate:* golden renders bit-identical; instruction counts not worse; sanitizers green; one shared library
fewer at runtime.

Target layout (D2):
```
engine/      core scheduler, graph, events, live edit       (was native/engine2 + control)
sdk/         module API header, C++ wrapper, helpers, template, checker   (MIT, self-contained)
modules/     one folder per module: dsp, tests, docs, optional ui/        (was native/modules2)
host/        sidecar, audio, midi, osc, patch document
targets/     web (wasm), later: daisy, clap
apps/        studio, desktop
tools/ bench/ facts/ proposals/ docs/
```

### Phase 2 — Edits never restart; protocol v1
1. **Edit operations instead of documents.** Undo, redo and snapshot restore become the difference
   between two documents, sent as ordinary edits. `loadGraph` remains only for opening a patch.
2. **State-carrying module replacement.** A config change builds the new instance off the audio thread,
   hands it the old instance's state, and swaps at a block boundary with a short crossfade (D10).
3. **Data is not config.** Sequencer steps, CC maps, OSC routes and similar become live module data sent as
   messages the module applies between blocks. Groove edits while running.
4. Modulation amount becomes a live parameter. Device and buffer changes keep the graph and its state.
5. **Protocol v1** from a single schema that generates the TypeScript types and the C++ validation;
   client edit queue fixed (pipelining, rollback, session handling); a heartbeat; blocking device work
   moved off the control thread.

*Gate:* the continuity test shows no phase reset and no silence for every edit listed in KNOWN_ISSUES A2;
you confirm by ear on the Pi.

### Phase 3 — Module format, SDK and tools
1. **Module API v3**: descriptor is the single source; `module.json`, the Studio catalogue and docs tables
   are generated. Declared capabilities replace ID special cases: note/MIDI/message ports, host services
   (MIDI device, OSC bus, tables/sample buffers, transport), structured telemetry, live data messages.
2. **Discovery**: the build finds module folders, in the tree or in outside directories. No lists.
3. **`wirescape module new | check | test`**: scaffolding, a checker that says what is wrong and how to
   fix it, and the standard test matrix (rates, block sizes, channels, reset, state, no allocation,
   NaN, denormals) run against any module with no test code written by the author.
4. **Portability tiers**, checked in CI: *portable* (float, no heap, no OS: compiles for Cortex-M7, eligible
   for the future patch compiler) and *desktop* (anything else). Basic modules move to the portable tier.
5. Shorter basic modules: host-side smoothing and voice iteration helpers so a VCA is its arithmetic.
6. **Proofs**: GUTTR dropped in with zero core edits; the out-of-tree trial passing on three platforms;
   one portable module running in a minimal Daisy firmware build and one as a CLAP plugin (thin adapters,
   build-only in CI).

*Gate:* targets "0 files edited", "out-of-tree passes", "0 module IDs in core".

### Phase 4 — Sound quality
One module per PR, each with before/after measurements and renders (D5). Order by measured severity once
Phase 0's metrics exist; the current candidates are: modulation smoothing policy (host-level, opt-out per
port); CHAOS band-limited oscillators; click removal (CHOKE, mode switches, bypass); VCF gain
compensation and Ladder feedback; reverb gain staging; Macro Oscillator at any sample rate; a single NaN
policy; envelope timing; rate-independent constants. VCO waveforms beyond sine if you want them.

### Phase 5 — Categories, capabilities and custom UIs
1. **Category infrastructure**, each proven by one real module:
   - *model-based multi-voice* (GUTTR): module-owned voices with group semantics, per-voice modulation
     inputs, per-voice telemetry, shared table cache;
   - *ported library* (Macro Oscillator): resampling/rate adaptation, block adaptation, third-party pin
     and licence handling;
   - *multi-part instrument* (CHAOS): sections, internal routing, presets.
2. **Stock modules that each bring a capability** (basic versions): Transport/Tempo (shared time),
   Sampler (sample-buffer service, file loading off-thread), Stereo Out and Bus (stereo/aux paths),
   MIDI Out, Scope/Analyser (structured telemetry), Wavetable Osc (table service), Logic/Math set
   (compiler-friendly primitives), Sub-patch (nesting, the unit the patch compiler will need), Recorder.
3. **Custom module UIs** (D7): panel package format, host API, sandbox, two worked examples (CHAOS,
   GUTTR). Groove and OSC editors move onto it, out of Studio core.
4. Raise the 64-module limit once UI frame times allow.

### Phase 6 — App, targets and release shape
Pi and Windows performance to target; Studio rendering at 200+ modules; installer/packaged build;
AudioWorklet web demo on the shared engine path; patch intermediate representation and the first strict
patch-to-Daisy compiler; the build page. This phase is mostly beyond the current three blocks.

## Risks

- **Deleting ABI1 removes a cross-check.** Mitigation: its renders are frozen as data first; golden
  renders of all bundled patches gate every merge.
- **Live state transfer is the hardest engineering here.** Mitigation: the continuity test exists before
  the work starts; each edit type lands separately.
- **API v3 designed too early for categories not yet built.** Mitigation: GUTTR, Macro and CHAOS are ported
  to it before it is declared stable; it stays "soft" until Phase 5 ends.
- **Hosted CI cannot hear.** Device runs remain the ground truth, and the plan has two owner checkpoints.
