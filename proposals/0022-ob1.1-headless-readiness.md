# 0022 — OB1.1 Tier 1: headless readiness (OSC, patch switching, Gate Delay, presets)

**Status:** accepted for implementation by the Claude Architect, 2026-11-25 (owner request, same day).
Reframed 2026-11-26 (owner): these are permanent headless requirements, not preparation for one event; rows unchanged.
**Contract:** [OB r2.12](../docs/workflow/milestones/OB.md), rows OB-h1 to OB-h6.

## 1. Why
The headless Pi 5 build must run for hours, unattended. Python generative scripts send OSC in. OSC
out drives LEDs and servos on one or more network controllers (any Wi-Fi board that speaks OSC).
Patches switch while playing. The owner designs those patches in the full Studio app, and the same
patch files must run unchanged on the headless build. That build is a separate supervisor process
in a separate repo (`wirescape-headless`, design by the 2026-11-26 Planner runs). It drives the unchanged
`wirescape-engine` over protocol v0 (`loadGraph`, `setParam`, `panic`, `status`).

Owner priority: playback stability, OSC reliability and patch switching come before perfect live
editing. A short, controlled recovery is better than a stalled player.

So Tier 1 holds only the work that sits in the engine, Studio or the shared tools. All of it
benefits the full app, and the headless build inherits it.

## 2. Rules for every Tier 1 row
1. **One patch file for every host.** No row adds a required patch key or makes a patch depend on
   the app, a preset file or a script. A v1-config module saves byte-identically (OB invariant B1).
2. **Devices off and no LAN in CI.** Network destinations are tested for parsing and refusal only.
   Packet tests use `127.0.0.1`.
3. **No loosening.** The OB-g8 profile (64 addresses × 200 Hz), the 50 ms gate rule, zero route
   drops, queue sizes and golden identity stay unchanged.
4. **Wall-clock gaps are facts, not pass marks** (OB r2.1). Correctness is gated.

## 4. OB-h2: OSC Out network destinations (A91)
`docs/specs/OSC_OUT.md` already reserves this: "A future LAN destination bumps `version` (and needs
`--confirm-lan`), so older engines refuse it."
- **Config version 2** adds an optional `host`, an IPv4 dotted literal. Hostnames and mDNS are out
  for now (the owner sets a static DHCP lease for each Pico). Port stays per module. A writer emits
  version 2 only when `host` is present and not `127.0.0.1`. Every other config stays version 1,
  byte-identical.
- **Permission.** A non-loopback `host` sends only when the owner's network permission is on (the
  same switch that lets OSC In bind the LAN: `--confirm-lan` / `setOsc.allowNetwork`). Without it
  the module sends nothing, and its route reports `lan-refused` in `status.osc`. It never redirects
  to localhost silently, because that would mislead.
- **Several boards.** Each OSC Out module has its own destination. Two modules must reach two
  destinations. The test uses two loopback ports.
- No change to rate, deadband, rows, notes or wire format. The realtime module still writes only
  the `OutBus`.
- **Split (SR21).** The engine and spec part ships first (B2). The Studio "Host" field in the
  OSC Out editor, with the same network warning as OSC In, follows OB-h5 because both edit
  `OscEditor.ts`.
- **Review.** Claude contract review is required, because this is a new network egress surface.
- **Overturned by:** a measured need for hostnames (then add a resolver on the control thread with
  a bounded timeout), or the owner choosing a Pi-side relay instead.

## 5. OB-h3: patch switching witness (A93)
The sidecar already fades the master out, swaps the stopped graph and fades in
(`host/sidecar/session.cpp`, `WS2_REPLACE_FADE_DEFAULT_MS`). Tier 1 proves the whole switch works
under OSC load and fixes only what fails.

A device-off test runs the null-audio sidecar with localhost OSC. Patches A and B each have `osc.in`
on 9000 and `osc.out` on 9001, plus a gate that is held across the switch. The test makes 200
alternating `loadGraph` switches (1000 in a dispatch variant). For each switch it asserts:
- the ACK is `ok`;
- the new OSC In route is listening, not port-busy, and a sentinel sent after the ACK arrives
  within 50 ms;
- no gate or MIDI note is held after the switch;
- the captured output fades to zero before the swap and rises from zero after it, using the
  engine's own fade, not a new threshold.

Recorded, not gated: gap ms and RSS at switches 100 and 1000. Leaks are gated by the ASan/LSan run of
the 200-switch test. Fixes go in the stage the test names. A product fix in `host/sidecar/` needs
a Claude contract review.

## 7. OB-h5: OSC presets (A92)
- **Built-in "Script (/ws/…)" preset for OSC In.** It is one fixed address scheme, so any script
  works with any patch built from it:

  | Row | Address | Kind | Range / notes |
  |---|---|---|---|
  | 1 | `/ws/pitch/*` | cv | MIDI note 0–127 mapped linearly so note *n* gives the same pitch CV as MIDI to CV for *n* (test: notes 0, 60, 127) |
  | 2 | `/ws/trig/*` | trigger | message alone fires |
  | 3 | `/ws/gate/*` | gate | 1/0, `timeout_ms` 2000, `stale` zero |
  | 4 | `/ws/vel/*` | cv | 0–1 |
  | 5–8 | `/ws/cv/1` … `/ws/cv/4` | cv | 0–1, smoothing 5 ms |

  The default for a new module stays the Pico rows. The existing built-ins stay.
- **User presets** for the OSC In and OSC Out editors use Save preset… / Load preset… (file
  dialogs). The desktop app also lists a presets folder (`<userData>/presets/osc/`) as buttons next
  to the built-ins, with "Open presets folder". The web build gets download and upload only.
- **File format:** `{"format":"wirescape.osc.preset","version":1,"module":"osc.in"|"osc.out","name":"…","config":{…}}`.
  `config` holds `port`, `rows` and, for OSC Out, `notes` and `rate_hz`. **A preset never carries
  network settings.** OSC In `lan` and OSC Out `host` stay as the patch has them. A preset loaded
  into the wrong module type is refused with a message.
- Applying a preset writes ordinary config rows. The patch format is unchanged. A Python script may
  read the same file to get its addresses. Document the format in `docs/specs/OSC_PRESETS.md`.

## 8. OB-h6: patch check tool (A94)
`python tools/patch_library.py check <folder> [--rate 48000 --block 128 --seconds 10]` renders
each patch offline with the compiled `wirescape_render`, the same path as `tools/patch_roundtrip.py`.
It opens no device. For each patch it reports:
- load ok, or the refusal reason;
- NaN/Inf sample count, peak and RMS;
- `silent`;
- p50/p99/worst block µs as % of the period, and overruns.

The output is a table plus JSON. It exits non-zero only for a load failure or NaN/Inf. Silence is
reported, not failed, because a patch may wait for external OSC. The owner runs it on the Pi before
copying patches.
