## Invariants (quoted in review requests)
- **G1** Render-thread cost of publication is one atomic exchange per block and one pointer
  assignment when a layout arrives. No allocation, lock, wait, I/O or logging is added to
  `render`, event dispatch or `reset`.
- **G2** Render never reads a layout after it has stored that layout's successor in
  `adopted_revision`. The control owner frees a layout or an instance only after it reads
  `adopted_revision` ≥ the revision that dropped it.
- **G3** One layout in flight. A second publish waits for adoption, bounded by three block
  periods; a stopped stream is swapped quiescently.
- **G4** Unchanged by M4: event ordering and budgets, the ingress and egress rings' ordering
  guarantees, clock anchors, parameter smoothing, feedback block size, poly rules, the FTZ/DAZ
  guard, and every existing module's behaviour when its descriptor does not use a new field.
- **G5** Additions to `module2.h` are at the end of their structs, guarded by `struct_size`. A
  module built against the header before the addition loads and behaves the same.
- **G6** With no edit in a render, output is bit-identical: golden 24 identical on three
  platforms on every PR. E4b and E5 change what an edit sounds like and nothing else.
- **G7** `adopt` and the data-slot read are realtime code: bounded, no allocation. `adopt` keeps
  no pointer into the old instance. A data pointer is valid for one `process` call.
- **G8** Instruction counts: no row more than 1 % worse on E6, E4a, E5, E3a, E7. E4b may cost up
  to 3 % on rows with ramping-capable edges, stated in the PR with the rows; more is an escalation.
